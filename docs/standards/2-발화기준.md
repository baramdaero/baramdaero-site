# 2. 발화 기준 — 카피 규율 (전 채널)

이 문서는 **신규 규칙이 아니다.** `CLAUDE.md` · `faq.json`의 `_설명` ·
`handoff/`에 흩어져 있던 기존 규칙을 옮겨 모은 것이다. 이관 대조표는 문서 끝에 있다.

적용 범위: 사이트 전 페이지, 챗봇, 블로그, 시공사례, 상황별 안내, 검색 노출 문구(메타·JSON-LD).

---

## 1. 말할 수 있는 것

### 자사 이행 주장 — 확정 3계열뿐

```
① 사전에 말씀드리지 않은 추가금 없음
② 작업 사진 전달
③ 단일 연락 창구
```

자사가 "~해 드립니다"라고 쓸 수 있는 건 이 셋뿐이다.
그 외의 약속(기간·무상·범위)은 규정이 확정되기 전에 쓰지 않는다.

### 출처 있는 사실 인용

시방서·공공기관 통계·법규는 출처를 병기하면 쓸 수 있다. 형식은 §4.

---

## 2. 말할 수 없는 것

| 금지 | 내용 |
|---|---|
| 기간·성능 숫자 | 보증 N년, N시간 내 연락, N% 절감, "1년에 1~2회" 같은 주기 단정 |
| "보증" | **제조사 보증을 지칭할 때만** 허용하고, 주어를 명시한다 ("제조사 보증 기간 안에…") |
| 최상급 | 최고·완벽·정직·꼼꼼 |
| 공포 소구 | 위협·불안 유발 문구 |
| 경쟁사명·업체명 | 비교 대상으로도 쓰지 않는다 |
| 고객에게 사진·문서 요구 | 우리가 작업 사진을 남겨 드리는 문구(②)는 유지 |
| 미출시 상품의 주기·항목 약속 | 정기관리 주기·포함 항목 등 |
| 근거 없는 수치 | 시공 수치는 실측값만. 실측이 없으면 그 문장을 쓰지 않는다 |
| 하도급 단가 | 공개 좌표는 소비자 시세만. 원가·하도급 단가는 산출물에 넣지 않는다 |

### 왜 "요구"를 못 쓰나

**요구를 지시하면 그 요구가 우리에게 돌아온다.** 주어가 모호한 요구 문장은
자사 이행으로 읽히고, 파트너 구조에서는 그 이행을 통제하지 못한다.
(2026-08-13 "보증 범위와 연락 방법을 문서로 받아 둡니다" 항목 삭제 근거)

### 표기·상태 규칙

- 샘플·더미 콘텐츠에는 `[샘플 — 실제 사례로 교체 예정]` 표시를 유지한다
- 내부 마커(`[현장 데이터 필요]`)가 고객 화면에 나가면 안 된다.
  마커만 지우면 근거 없는 문장이 남는다 — **문장째** 지운다
- 가격 숫자는 `faq.json`의 `price_note`와 `pricing.json`에만 쓴다. 9월 원가 산출 후 기입
- 확정 전 값은 비운다. 빈 값이면 그 줄·항목이 조용히 빠지도록 코드가 처리한다

## 3. 채널 동기화 — 정책이 바뀌면 전 채널을 훑는다

서비스 범위·가격·기간·약속에 해당하는 정책이 바뀌면 한 곳만 고치고 끝내지 않는다.

| 채널 | 확인 지점 |
|---|---|
| `faq.json` | 본문 `a` + `chat_a` (둘이 다른 값을 가질 수 있음) |
| `Chatbot.astro` | `COPY`, `NODES`, `TREE_START` |
| `config.js` | `WELCOME_MESSAGE`, `RESPONSE_NOTE` 등 상수 |
| `home.json` / `standards.json` | |
| `situations` / `cases` / `blog` | |
| 각 페이지 하드코딩 문구 | |

**검사는 dist 전수 grep으로 한다** (HTML + 번들 JS 모두).
소스만 보면 챗봇 COPY가 번들로 들어가 HTML grep에 안 잡힌다.
절차와 grep 패턴은 `CLAUDE.md` §카피 작업 완료 조건.

### 실제로 샌 사례 (2026-08)

1. FAQ "2년간 무상" 제거 → 챗봇 `as.when`에 생존
2. 세척 본문 교체 → `chat_a` "1년에 1~2회"가 본문과 모순
3. 챗봇 카피 재작성 → `config.js` "1시간 안에" 생존
4. 챗봇 이전 설치 제거 → FAQ 2문항이 "확인해 드린다"로 생존

방향은 양쪽 다다 — 페이지를 고치면 챗봇에 남고, 챗봇을 고치면 페이지에 남는다.

## 4. 출처 표기

| 인용 | 표기 |
|---|---|
| 시방서 | 삼성전자서비스 「에어컨 세척 표준시방서」(2025) |
| 통계·기관 | 기관명 + 연도 |
| 자사 실측 | "자사 시공 기록 기준" + 시점 |

블로그는 프론트매터 `facts[].source` / `sources[]`에 넣는다 — 출처 없는 사실은 `facts`에 올리지 않는다.

## 5. 채널별 제약

### 챗봇 (`Chatbot.astro`)

- **한 줄 상한 한글 25자.** 360px·데스크톱 패널 모두 말풍선 279px로 동일 (실측)
- 되묻기는 노드당 1개
- FAQ 본문으로 보내는 링크 칩은 남발하지 않는다
- 막다른 답변 금지 — 유도 칩이나 홈 메뉴가 반드시 따른다
- 긴 마크다운 본문을 `chat_a`에 넣지 않는다. 짧은 답이 없으면 비워 둔다
  (비면 그 문항만 챗봇에서 빠지고 `/faq/` 본문은 그대로 나온다)

### FAQ (`faq.json`)

- `hook`은 통념 부정·되묻기만. 공포 금지
- `related`의 블로그 연결은 글이 나온 뒤에 건다
- `hold` 문항은 화면·챗봇·검색엔진 모두에서 빠진다.
  해제 조건 5분류(사업자등록 / 9월 원가 / 작업표준 / 운영규정 / 실적)는 `faq.json` `_설명`

### 홈 (`home.json`)

- 우리가 무엇을 하는지 선언하는 **1인칭**으로 쓴다
- 고객에게 말을 거는 2인칭은 맨 아래 CTA에서만

### 히어로 아래 다크 구간 (`hero-worldview.json`)

- 1인칭 복수
- 이 구간에는 2인칭·CTA·판매 문구를 넣지 않는다

### 톤

문장 톤 규칙(이모지·감탄사·수사적 질문 금지, 형용사 대신 구체 명사,
문단 2~3문장, 모바일 360px 기준)은 `DESIGN.md` §7이 원본이다.
UI 작업 전 필독 문서라 그 자리에 둔다.
